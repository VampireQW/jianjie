# R292

“优先低延迟”开启时，将投屏接收器自身 Direct3D 设备的预排队上限设为 1 帧，减少画面提交后的等待。通过 GStreamer 的 present 回调取得实际渲染设备，设备重建后重新应用；不支持该接口或设置失败时继续原有渲染。关闭低延迟模式时保留原来的同步方式。

画质、最高帧率、蓝牙控制协议、发现方式和媒体运行库均未改变，也不修改系统显卡或防护设置。接收器原生文件比 R291 增加 512 字节；最终 EXE 大小以构建验证报告为准。

依据：R291 真机 35 秒采样共 1,480 帧，PresentMon 测得接收器 Present 至实际显示的等待中位数 17.200 ms、P95 38.361 ms、最大 47.026 ms。这些指标不包含手机编码、网络回传和蓝牙输入，不能当作完整操作延迟。

验证：42 项针对性的显示、输入、界面、组件及打包保护检查通过，其中真实私有 Direct3D WARP 设备确认排队上限从默认 3 帧变为 1 帧，并检查不支持接口时的回退。真实显卡回调是否生效、上屏时序变化和用户体感仍以真机复测为准。旧的全量自检未重复执行，R290 已记录的无关失败项没有宣称通过。

真机复测（2026-10-28）：已验证真实渲染设备的上限从 3 帧设为 1 帧。35 秒内采到 1,871 帧，均有显示记录；Present 至显示的中位数为 21.543 ms、P95 32.737 ms、最大 33.851 ms。与前一次采样相比，P95 和最大值下降，中位数上升；两次操作内容和帧数不同，不能据此宣称完整链路或所有帧都更快。用户反馈“有改善，但仍有延迟”，因此视觉延迟尚未完全解决。

正式 EXE 为 40,316,791 字节，比 R291 增加 3,603 字节。正常全量构建误收的 OpenSSL 与 pthread 媒体依赖已从主 EXE 移除，媒体运行库继续使用独立组件；没有改变功能或安全设置。
